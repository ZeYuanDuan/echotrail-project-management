## 二、目前未決事項（開放問題彙總）

### 🚩 team 內部有分歧，需要開會拍板（優先）

1. **C-7／C-8／C-9 職涯錨點／RIASEC／DISC 三項測評分數的資料來源**：夥伴主張 LLM 直接從對話內容推論產出；Webber 主張需要使用者實際填答一份標準化量表，分數才可信。260901 夥伴補充了「LLM推論」這條路完整的技術方案（逐事件記分、累加平均，見下方260901條目），已寫入 SPEC C-7／C-8／C-9 作為目前記錄的方案，**但這只是把其中一方的提案細節補完整，team尚未正式拍板要走哪一條路**，SPEC內已加註🟡標示不代表定案。
2. **三項測評是否共用同一套技術方案**：260901 補充的技術方案顯示三者確實可以共用同一套「逐事件記分、累加平均」邏輯，差異只在面向數量（8/6/4）與最終視覺呈現（雷達圖/長條圖/象限圖）。此點技術上已可行，但仍附屬於第1項分歧——只有在team選定「LLM推論」這條路之後，這套共用方案才會真的被採用。
3. **C-10 增量更新規則：哪些分數允許隨新事件微調、哪些鎖定不變**：260901 補充的技術方案是三項測評**都會**隨新事件微調（逐事件記分、累加平均），與 demo 腳本「職涯錨點微調但RIASEC/DISC不變」的舊示例不一致。若team採用LLM推論這條路，這項分歧可望自然解決（三者都用同一套會微調的邏輯）；若team選擇量表填答，則應維持鎖定不變。

### 待技術評估／實測

4. **登入「名字→使用者ID」對應規則未定義**：目前只定案「輸入名字即可進入」，但撞名怎麼處理、名字唯一性要不要檢查、換裝置／清瀏覽器資料後能否用同一個名字找回原本的使用者ID，完全沒有規則。這會直接影響使用者資料會不會互相覆蓋或遺失，屬於**工程開始實作前必須先有答案**的項目，不是可以晚點再補的UI細節，見260830／260901條目。
5. **A-2 履歷自動解析的 MVP 技術可行性**：待與工程 team 確認 PDF/DOCX 解析的工作量，若有困難需重新評估是否退回手動表單。
6. **A-4 總輪數軟／硬上限的具體數字**（例如3輪／8輪）：目前僅為示意值，待實測校準。
7. **B-2 匹配分數區間對應的文字判讀門檻**（例如幾分以上算「高度符合」、幾分以下算「落差明顯」）：具體數字尚未定義，需要跟「內部信心分數」機制對照，避免兩套邏輯不一致。
8. **B-2 內部信心分數的計算方式**：與匹配分數（已定案為LLM自評）是否要統一成同一套邏輯，尚未討論。
9. **A-3 語音輸入的技術方案**：瀏覽器原生 Web Speech API 還是接第三方 STT 服務、中文辨識準確度能不能接受、是否需要額外的錯字修正機制，尚未評估，見260830條目。
10. **A-4 System Prompt 草稿尚未定案**：夥伴提供的艾可 System Prompt 草稿已寫入 SPEC，但仍是草稿——需要跟工程 team 一起測試「先讓使用者感覺被聽懂，再收集結構化資訊」這個順序，實際 LLM 輸出會不會不小心洩漏系統內部術語（事件具體度、情緒明確度等），以及這份 prompt 跟既有「三段式回應結構」「反問決策規則」兩套機制整合起來是否會互相矛盾，都需要實測驗證後才能定案，見260901條目。
11. **A-5〈產生洞察〉保留字指令是否雙向觸發**：按鈕點擊會自動送出「Please Generate my insight」這組特殊指令，但使用者自己在對話框手打出一模一樣的句子時算不算數，目前沒有定案；若要辨識，工程實作上需要明確定義這組保留字、並跟一般使用者輸入內容做區分，避免誤判，見260901條目。
12. **「和過去的我是否匹配」欄位的視覺呈現，B-2文字定義與Figma畫面不一致**：B-2現行定義是「0-100分＋文字判讀＋符合/落差關鍵字對照」；260901補充的Figma畫面卻顯示雙色圓環圖（金色＝跟過去相似比例／核心特質，綠色＝新發現比例），且該處註記「規則：待定」。這不是單純的UI風格差異，兩種呈現方式背後的計算邏輯也不同（分數比對 vs. 比例圓環），需要team決定最終要用哪一種，並回頭同步修正B-2或A-5其中一邊，見260901條目。
13. **Echo Card 效能疑慮**：Figma畫面備註「洞察卡片其實有效能問題」，具體是LLM多欄位生成的回應時間、還是其他技術瓶頸，目前完全沒有說明，待team進一步釐清問題本質後才能評估解法，見260901條目。
