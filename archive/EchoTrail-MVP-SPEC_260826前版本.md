# ▌Background & Goal

## Background

目標客群是**職涯卡關、卻怎麼想都說不清楚自己卡在哪裡的人**，優先測試對象為兩位persona：羽絨（經驗零散者）、Webber（自我整理卡關者）。核心痛點有二：

1. **主客觀的剝離**：使用者的客觀職涯紀錄與真實主觀感受分開存在，沒有人把兩者放在一起比對。
2. **沒有好的框架/格式能完整呈現並反覆迭代**：即使使用者自行使用生成式AI，也需要具備prompt調校能力才能得到貼近自己的輸出，多數人做不到。

## Goal

驗證「拉取客觀職涯紀錄＋對話收集主觀語料＋交叉比對＋結構化呈現」這套流程，能否產出使用者自己跟AI聊天達不到的洞察品質，作為後續是否投入完整自動化引擎工程的判斷依據。

## 三個核心功能與各自解決的問題

| 功能 | 解決的問題 | 對應 |
|---|---|---|
| A．對話與輸入 | 多數人講不清楚自己的職涯歷程，也不具備prompt調校能力，自己跟生成式AI聊沒辦法整理出結構化、貼近自己的輸出 | Background痛點2 |
| B．時間軸與洞察 | 客觀職涯紀錄與真實主觀感受分開存在，沒有人把兩者放在一起比對，看不出「客觀上一切正常」跟「主觀上哪裡不對勁」之間的落差在哪 | Background痛點1，也是核心假設要贏過免費生成式AI的地方 |
| C．儀表板 | 累積了一堆事件記錄，也很難自己歸納出「這段時間展現過哪些能力」——主客觀落差之外的另一種自我覺察需求 | 本輪新排入Part 1，非Background原始痛點的延伸 |

# ▌Spec

## Scope

**Part 1（本版）**

A．對話與輸入
- 客觀資料匯入（履歷/工作紀錄基本欄位）
- 冷啟動對話（收集主觀語料）
- 快速匯入（貼上舊資料批次產生事件，冷啟動對話的批次版本）
- 事件時間判斷與確認（解析事件實際發生時間，抓不到時追問使用者）
- 專案／階段標籤（選填，標記事件所屬專案或階段）
- 確認式對話（針對候選落差點追問確認）

B．時間軸與洞察
- 時間軸呈現（純時序，不含主線／支線區分與落差點視覺標記）
- 與洞察的連結（時間軸節點提供錨點，供逐事件／整體洞察回頭定位）
- 逐事件洞察呈現（雙證據格式）
- 整體洞察呈現（跨事件模式，至少引用2個以上事件）

C．儀表板
- 能力傾向儀表板（沿用客觀詞彙頻率統計，重新詮釋為能力/技能傾向排行，純規則型不涉及AI推論）

- Process採輕量AI prompt（單一prompt呼叫既有LLM API），非完整自動化引擎

**Part 2（後續，本版不做）**
- 完整自動化比對引擎（多步驟pipeline、模型微調，取代單一prompt）
- 時間軸的主線／支線視覺區分、落差點視覺標記
- 使用者手動標註事件為落差點的功能（獨立於AI洞察機制之外，需另外評估）
- 依專案／階段標籤篩選或分組顯示的操作畫面（本輪僅存標籤資料）
- 時間軸最少事件數門檻的統一規則
- 「猜測時間」與「使用者確認時間」的圖示化區分（目前僅以文字說明區分）
- 逐事件洞察／故事草稿區
- 情緒折線圖、Persona自我畫像卡
- 職能儀表板、模式圖書館、決策紀錄、成就牆
- 匯出／分享功能、工作機會雷達
- 輕推通知（排程／事件trigger）
- 持續迭代精進（Should Have層驗證）

## Function Detail

**A．對話與輸入**（解決的問題見文件最上方總覽表）— 負責把使用者原始輸入（不管是聊出來的還是貼上來的）轉成結構化、時間與專案標籤都判斷好的事件資料，交給B組陳列。不負責時間軸怎麼排序呈現，也不做洞察分析。

### A-1　客觀資料匯入

👤 **User Story**
As a 職涯卡關、想搞懂自己卡在哪裡的使用者
I want 匯入我的履歷或工作經歷
So that 系統能拿我的客觀職涯軌跡去跟我的主觀感受比對

**功能概述**：使用者上傳履歷檔案或手動填寫基本職涯經歷欄位，作為比對引擎的客觀資料來源。

- 支援上傳PDF/DOCX履歷檔案，或手動填寫欄位（公司名稱、職稱、任職起訖時間、簡短職責描述）
- 至少需要涵蓋2段以上職涯經歷才能進入下一步
- 此為必填項目，不可跳過
- 🟡 待確認：本輪是否需要真的做履歷檔案自動解析，或先用手動填表單即可

### A-2　冷啟動對話

👤 **User Story**
As a 沒有現成日記/貼文可匯入的使用者
I want 透過輕量對話講出最近的感受
So that 我不需要先準備好資料就能開始使用

**功能概述**：以一問一答、鏡映再追問的對話形式，引導使用者說出具體事件與感受，收斂成事件卡，作為比對引擎的主觀資料來源。

- 每輪僅問一題，開放式自由輸入，不提供選項
- AI每次先簡短回應/認同使用者上一句話，再問下一題
- 每題可Rephrase（換個問法）或Skip（跳過）
- 收滿3-5張事件卡自動結束；使用者亦可主動喊停
- 超過10輪仍未收滿，則以現有資料先進入分析階段
- 🟡 待確認：事件卡的最小必要欄位（時間／情境描述／感受用字）如何轉換成後續prompt的輸入格式

---
**驗證用途**：確保對話流程真的有把資訊收齊才進入分析，不能收集不完整就提前產出洞察。
- 進入B-3分析階段前，須檢查對話流程是否已收集到足夠的主觀語料（至少涵蓋事件、情境、感受用字三個面向），未收集完成不應提前進入分析
- 團隊checklist逐一檢查每一輪對話收集，記錄「資訊蒐集完整才進入分析」的命中率

### A-3　快速匯入

👤 **User Story**
As a 已經有履歷、日記、舊貼文等既有資料的使用者
I want 一次貼上多行舊資料，讓系統批次產生事件記錄
So that 我不用透過一問一答的對話，一筆一筆重新講一次

**功能概述**：讓使用者一次貼上多行文字，逐行解析後批次產生事件記錄，是A-2冷啟動對話之外的另一種輸入方式，UI位置與對話收集引導同頁。

- 入口與對話收集引導同頁，作為對話框下方的另一種輸入選項，不是獨立分頁
- 貼上的文字以換行分隔，每一行視為一則事件，套用與對話收集相同的分類規則（主觀／客觀／混合、情緒、具體度）
- 每一行各自獨立解析時間與專案標籤（規則見A-4、A-5）
- 匯入完成後自動切換到時間軸分頁呈現結果（結果呈現屬於B-1職責）
- 匯入產生的事件會標示「匯入」來源，與對話收集產生的事件（標示「對話」）在B-1區分顯示
- 🟡 待確認：快速匯入的資料本質上是主觀語料的批次回填，跟A-1（客觀職涯紀錄匯入）性質不同，命名與編號是否需要進一步跟A-1做區隔以免混淆

### A-4　事件時間判斷與確認

👤 **User Story**
As a 講述一件不是發生在「現在」的事情的使用者
I want 系統正確辨識或主動詢問這件事實際發生的時間
So that 這則事件能被放到時間軸上正確的位置，而不是被誤植在「現在」

**功能概述**：解析事件內容中的時間資訊以決定其排序位置；抓不到明確時間時主動詢問使用者確認，不用預設值蓋過去。此功能發生在事件被收集的當下（無論來自A-2對話或A-3快速匯入），輸出結果交給B-1時間軸使用。

**解析規則**：判斷事件實際發生時間的優先序。
- 解析優先序：絕對日期格式（例如「2022/03」）> 相對時間用詞（例如「半年前」「上個月」）> 都抓不到則進入追問流程

---
**對話收集路徑的追問**：發生在一問一答的對話情境中。
- 使用者確認事件內容無誤、且系統抓不到明確時間時，才追加一句時間提問
- 使用者仍答不出來（回覆「不確定」）時，標記為「現在（未確認時間）」並繼續流程，不卡關

---
**快速匯入路徑的追問**：發生在批次貼上舊資料的情境中，銜接A-3。
- 能解析出明確時間的行直接匯入；抓不到的行整理成清單，逐行顯示原文並附上時間輸入欄
- 使用者逐行補填或留空／填「不確定」，確認後才一併送入時間軸

---
**明確來源標示**：確保猜測與確認不被混淆，此標記會一路帶到B-1顯示。
- 「使用者親自確認的時間」與「系統推測用的現在時間」須在資料上明確區分，供B-1呈現時不可讓兩者外觀相同
- 🟡 待確認：目前只靠文字說明區分（例如「現在（未確認時間）」），是否需要額外的圖示區分

### A-5　專案／階段標籤

👤 **User Story**
As a 同一個專案在不同時間點留下多筆事件記錄的使用者
I want 幫事件標記所屬的專案或階段
So that 之後回顧時能看出這幾筆事件其實是同一條線，不用自己記

**功能概述**：讓事件在被收集當下可選填標記所屬專案或階段，取代複雜度過高而排除的主線／支線視覺分支，用輕量標籤在B-1達到類似的辨識效果。

- 對話收集路徑：時間確認完成後，多問一句「這件事屬於哪個專案或階段嗎」，使用者可回覆「跳過」略過不標記
- 快速匯入路徑：於該行文字後加標記語法（例如行末加`#A專案`），系統自動擷取並從內容中移除，不影響事件內容本身的分類判斷
- 標籤資料會一併交給B-1的時間軸卡片顯示，與時間、來源標籤並列
- 🟡 待確認：是否需要「依專案篩選／分組檢視」的操作畫面，或本輪僅驗證標籤資料本身有沒有人願意填、填的品質好不好

### A-6　確認式對話

👤 **User Story**
As a 已經產出候選落差點的比對流程
I want 針對每個候選落差點向使用者確認
So that 洞察的證據來源是使用者親自確認過的，不是AI/人工單方推論

**功能概述**：針對比對流程找出的候選落差點，逐一附上具體證據向使用者提問確認，使用者可選擇快速回覆選項或自由輸入。

- 每則提問須先陳述「我們注意到什麼」（具體引用客觀時間點＋主觀用詞），再提出問題，不可憑空問感受
- 提供3個猜測性快速回覆選項＋開放式輸入欄位
- 可Skip，跳過的落差點標記為「未確認／低信心」，不直接捨棄
- 處理完3-5個候選落差點後結束

**B．時間軸與洞察**（解決的問題見文件最上方總覽表）— 負責把A組已判斷好的事件資料，依實際發生時間陳列成時間軸，並在此之上呈現AI比對出的洞察內容。不負責決定事件的時間或標籤怎麼判斷出來（那是A組的職責）。

### B-1　時間軸呈現

👤 **User Story**
As a 走完輸入流程的使用者
I want 用視覺化時間軸看到我的職涯軌跡
So that 我能快速定位每個事件發生的時間點與位置

**功能概述**：以A組（A-2／A-3／A-4／A-5）已判斷完成的事件實際發生時間排序陳列所有事件，是時間軸的視覺呈現本體，只負責陳列不做判斷、不做時間或標籤的解析。

**核心原則**：時間軸的可信度來自於「誠實陳列、不夾帶判斷」。
- 事件依「事件實際發生時間」由舊到新排序呈現，不受輸入先後順序影響——使用者今天講一件半年前發生的事，這則事件要插進時間軸中間該在的位置，不能因為是今天輸入的就排在最後面
- 日期區間不設上限或固定顆粒度，可以是數月的單一專案回顧，也可以是橫跨數年的職涯歷程，由實際輸入資料決定，不預設短時間範圍

---
**資料結構**：每個事件節點需包含足夠欄位供渲染與跟B-2互相連結。
- 欄位：事件ID、事件實際發生時間（排序用）、時間顯示標籤（呈現用）、時間明確來源（布林值）、事件描述、感受描述、來源（A-2對話／A-3匯入）、專案／階段標籤（若有）

---
**情緒視覺**：每個事件節點左側圓點依情緒傾向呈現對應顏色。
- 顏色僅分正向／負向／中性三種，用途是讓使用者一眼掃過去感受整體起伏的大致形狀
- 此判斷不代表精準情緒分析，精準分析屬於B-3／B-4洞察機制的職責，時間軸的圓點不應被過度解讀成結論

---
**空狀態**：完全沒有累積任何事件時，顯示提示文案引導使用者回到A-2對話或使用A-3快速匯入。
- 🟡 待確認：目前1筆事件即正常顯示，沒有設定最少事件數門檻，是否需要門檻設計

---
**明確排除**：使用者手動標記事件為「落差點」的功能（例如點擊星星自行標註）不在本輪範圍內。本產品的落差點是AI比對客觀與主觀資料後產出，不是使用者自行標註；若團隊認為使用者自行標註有價值，應視為獨立功能另外評估，不要跟AI洞察機制混在同一個標記系統裡，以免使用者混淆「這是AI找到的」還是「這是我自己點的」。同理也不做主線／支線視覺分支（MAIN/BRANCH）。

### B-2　與洞察的連結

👤 **User Story**
As a 已經在時間軸上累積事件、也看過AI洞察的使用者
I want 洞察內容能連結回時間軸上對應的事件節點
So that 我不用自己在時間軸上一個個找，就能確認洞察講的是哪些事

**功能概述**：時間軸上每個事件節點保留可被引用的錨點，供B-3／B-4洞察文字連結或高亮對應節點，是B-1時間軸與B-3／B-4洞察功能之間的橋接機制。

- 每個事件節點需有唯一且穩定的ID，供洞察功能建立連結引用
- 洞察文字中提及的事件，須能透過此ID對應回時間軸上正確的節點
- 🟡 待確認：點擊洞察裡的引用文字時，時間軸節點的呈現方式是捲動置中、或是高亮閃爍提示

### B-3　洞察呈現（雙證據格式）

👤 **User Story**
As a 想知道自己真正卡在哪裡的使用者
I want 看到AI找出的落差點洞察，並附上具體證據
So that 我能相信這個結論不是空泛的建議，而是真的看過我的資料

**功能概述**：呈現比對流程產出的整體洞察，每條洞察須同時包含客觀時間點與主觀語句的具體引用，格式須讓未參與對話的第三人也能快速理解重點。

**資料結構**：每條洞察需包含可追溯的雙重證據，不能只是一段泛泛文字。
- 欄位：洞察ID、洞察文字、客觀證據（引用的事件ID＋日期＋具體欄位內容）、主觀證據（引用的原句文字＋來源事件ID）、狀態（已確認／待確認／已忽略，對應A-6確認式對話的結果）
- 客觀證據與主觀證據皆為必填欄位，缺一則此條洞察不可呈現給使用者（不可用「僅客觀」或「僅主觀」的洞察湊數）
- **使用者契合度**：1-5分，使用者針對這條洞察自行評分，介面呈現為可點選的圓圈；用於優化模型與判斷Nice to Have層（使用者意願）
- **內部信心分數**：1-5分，AI/團隊對這條洞察證據強度的自評分數，**對一般使用者隱藏**，只有團隊/研究用途看得到，用於後續排序與模型校準

---
**內容規則**：洞察文字本身要指出具體對應關係，不能是通用建議。
- 禁止使用「你可能需要...」「建議你...」這類泛用建議句型，須改為陳述觀察到的具體對應（例如「你在O月O日的△△事件中用了『XX』這個詞，跟你YY事件的客觀紀錄形成落差」）
- 本輪MVP單次分析須產出 **1至3條** 洞察，超過3條時僅呈現信心度最高的前3條（信心度定義：是否有明確的雙重證據支撐）
- 若比對後找不到任何符合雙證據條件的落差點，顯示空狀態提示，不可為了有東西呈現而放寬證據門檻硬湊一條

---
**呈現格式**：引用證據的顯示方式須格式統一，方便第三方快速辨識。
- 主觀原句以引號包框呈現，並標註出處（例如「『我變成在看報告』——2023/06」）
- 客觀時間點以日期標籤呈現，與B-1時間軸的日期格式一致
- 每條洞察須明確連結或鄰近呈現對應的時間軸節點（透過B-1／B-2定義的錨點機制），使用者或第三方測試者可直接對照，不需要自行在時間軸上搜尋
- 🚩**主觀證據必須是逐字引用，不能是摘要或標籤式改寫**——這條規則必須用程式做子字串比對（檢查引用文字是否為A-2原始逐字稿的精確substring）強制檢查，不能只靠人工讀起來像不像來判斷。團隊在建立demo資料時曾誤把摘要用的標籤詞當成逐字引用使用，讀起來很像但比對後不是逐字，這個問題只有靠自動化比對才抓得出來

---
**驗證用途**：此區塊是團隊checklist評分與第三方計時測試的直接測試對象，格式設計需直接服務這兩項測試。
- Checklist測試：逐條檢查是否同時具備客觀＋主觀證據欄位
- 計時測試：測量第三方測試者從打開此畫面到能正確說出「落差點是什麼」所需時間，並與純文字版本比較

### B-4　整體洞察（跨事件模式）

👤 **User Story**
As a 已經看過逐事件洞察的使用者
I want 看到一段整合多個事件、指出反覆出現模式的整體洞察
So that 我能理解自己不是單一事件卡住，而是有一個持續存在的模式

**功能概述**：呈現跨越多個事件、綜合分析後產出的整體洞察，指出使用者反覆出現的模式，是B-3逐事件洞察之外，測試「跨資料源比對」這個核心差異化主張的關鍵功能——單一事件的對應關係，使用者自己貼一段話進Claude也可能問得出來；但跨越多個事件才浮現的重複模式，才是結構化比對引擎真正該贏過使用者自行使用生成式AI的地方。

**資料結構**：與B-3逐事件洞察結構相似，但證據須來自多個事件。
- 欄位：整體洞察ID、洞察文字、引用的事件清單（至少2個不同事件ID，各自附日期＋客觀證據內容＋主觀證據原句）、狀態（已確認／待確認）
- 引用事件數須為2個以上，若比對後找不到跨越2個以上事件的共通模式，不產出整體洞察，只保留逐事件洞察

---
**內容規則**：整體洞察必須是「模式」，不是單一事件結論的重複轉述。
- 洞察文字須明確指出「這個對應關係在哪幾個時間點反覆出現」，例如「你在O月的△△事件與O月的☆☆事件裡，都用了類似『XX』的說法，但客觀紀錄顯示...」
- 禁止只是把某一條逐事件洞察換句話說一次當作整體洞察
- 本輪MVP最多產出 **1條** 整體洞察，找不到符合條件的跨事件模式則不呈現，顯示空狀態提示

---
**呈現格式與位置**：整體洞察是使用者進入洞察區看到的第一個內容，逐事件洞察在其後或需要時展開查看。
- 整體洞察卡片呈現在所有逐事件洞察卡片之前（先看大局，再看細節）
- 每筆引用證據需標明來源事件的日期，格式與B-3一致
- 整體洞察**不設**「使用者契合度」評分欄位（與B-3不同）——契合度評分保留在逐事件層即可，整體洞察的驗證改用下方的量化對照指標，避免同一份洞察被兩套機制重複評分造成混淆

---
**驗證用途**：此功能是驗證EchoTrail比對引擎能否贏過使用者自行使用免費生成式AI的主要測試對象，需要用可自動計算的量化指標，不能只靠主觀感覺判斷「贏了沒」。單一事件的對應關係，使用者自己貼一段話進Claude也可能問得出來；但跨越多個事件才浮現的重複模式，才是結構化比對引擎真正該贏過使用者自行使用生成式AI的地方，所以用這個功能作為主要測試對象。

對照實驗設計：同一份客觀職涯紀錄＋主觀語料，一組讓使用者自行貼進Claude/ChatGPT問「有沒有模式」，一組走EchoTrail完整流程，用下列指標比較兩邊輸出：

| 指標 | 定義 | 怎麼算（機器可自動檢查） |
|---|---|---|
| 具體時間點引用率 | 論點裡有幾成附上精確日期 | 逐句檢查是否含日期標記，算百分比 |
| 原句引用率 | 論點裡有幾成是逐字引用原話，不是改寫摘要 | 程式比對輸出文字是否為A-2逐字稿的精確子字串 |
| 跨事件證據數 | 單一洞察引用了幾個不同時間點的事件 | 計算引用的相異事件ID數量 |
| 建議語氣出現率 | 「建議你」「你可以」「或許」這類指導性語句出現次數 | 關鍵詞比對，算次數 |

前四項可自動化檢查，不需要等真人受測者；以下兩項需要真人受測者才能拿到數據，SPEC其他章節已定義：
- 使用者契合度（見B-3資料結構）：同一批受測者對兩邊輸出各自評分，做成對比較
- 第三方定位時間（見B-3驗證用途）：測量從打開畫面到能說出「落差點是什麼」所需秒數

### C-1　能力傾向儀表板

👤 **User Story**
As a 已經在時間軸上累積一些事件的使用者
I want 看到自己過去展現過的能力／技能傾向排行
So that 我能快速知道自己過去比較常用到、比較擅長的是哪些能力

**功能概述**：沿用B組事件資料裡的客觀詞彙（例如簡報、企劃、客戶溝通等），統計出現頻率，重新詮釋為使用者的能力／技能傾向排行，是規則型的輕量統計，不涉及AI推論或情緒判斷。

- 統計來源：所有事件的客觀詞彙（沿用A組分類邏輯裡的客觀詞彙庫），依出現頻率排序取前6名
- 呈現形式：長條圖形式的能力／技能排行榜，比照現有原型的關鍵字排行榜UI
- 純規則型統計，不使用AI生成內容，不對使用者的能力強弱做主觀評價或建議
- **明確排除**：不做情緒相關的統計呈現（原型裡的「我是誰摘要」「情緒走勢」屬於情緒面向，跟「能力」是不同概念，不歸在能力儀表板範圍內；若團隊認為情緒趨勢仍有價值，應視為獨立模組另外評估）
- 🟡 待確認：目前的客觀詞彙庫是否需要擴充或分類成更明確的「能力類別」（例如溝通類／專案管理類／技術類），或先用現有詞彙庫的原始頻率排行就好
- 🟡 待確認：資料量太少時（例如少於3則事件）的空狀態或門檻設計
