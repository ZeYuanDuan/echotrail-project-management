# 艾可 System Prompt v1 → v3 變更說明（給前後端）

給前後端的話：這次是架構級改動，不是小幅修字，主要是 Dashboard（④）的資料處理方式整個換了一套邏輯，加上①②③也連動調整，麻煩兩邊都花時間看一次，尤其標了「前端」的部分。

## 這次為什麼要大改

原本④是設計成「維護一份快照，每次拿新事件跟快照做增量比對」，後來拍板改成「每次都把該使用者全部歷史事件從 DB 撈出來，整批重新分析、重新產出」，原因是這次 MVP 優先撐住月會 Demo，全量重算實作上更簡單、更不容易出錯，即使效能不是長期最優解也先這樣做。這個架構調整往前牽動了①②③的一些規則，所以四份都有改。

## 五個主要變更點

1. **④ 從增量比對改成全量重算**：不再讀「上次的快照」，改成每次觸發都撈這個 user 全部歷史事件的欄位資料，重新產出 Dashboard 五個區塊。
2. **③多了一個使用者看不到的隱藏欄位**：Echo Card 確認產出後，③要額外判斷這次事件屬於 8 種職涯錨（Schein Career Anchor）的哪一種，或標記「無法明確歸類」，直接寫入 DB，不顯示在卡片畫面上。
3. **原本的「我的價值主張」欄位拆成兩個獨立子欄位存 DB**：`value_statement_summary`（總結）跟 `value_statement_quote`（逐字引證原話），畫面上仍合併顯示成一個卡片欄位，但資料庫要存成兩欄，方便④直接讀取原話不用自己解析。
4. **①②不再依賴外部的 Grounding Checklist 文件**，規則已經內嵌進①②③自己的文字裡，之前如果工程那邊已經串了那份文件進 context，這次可以拿掉。
5. **④的五個 Dashboard 區塊（B-1、B-2、B-3、B-4、B-7）重新寫過**，職涯錨的分數計算（B-7雷達圖）由後端計數，④的 LLM 只負責文字解讀，不算分數。

## 後端要特別注意

- DB 要新增／調整的欄位：`event_id`（之前沒有，這次補上，每筆事件的唯一識別碼）、`career_anchor_type`（8種標籤或「無法明確歸類」）、`value_statement_summary` / `value_statement_quote`（原本合併的欄位拆成兩欄）。附的 CSV 範例可以直接當測試種子資料。
- 職涯錨排序分數列表（B-7雷達圖用的分數）本質上就是這個使用者各職涯錨類型的事件次數（或次數佔比），怎麼換算成 0-100 分是工程自行決定的實作細節，不需要另外跟 PM 確認公式，只要能讓 8 個軸的相對高低準確反映次數差異就好（例如次數最多的那一軸應該分數最高）。
- ④呼叫時要傳的是「這個使用者全部歷史事件的欄位資料」＋「後端算好排序的職涯錨分數列表」，**不要**把對話逐字記錄也塞給④，那份資料④用不到，塞了只是浪費 token。

## 前端要特別注意

- **`<r>...</r>` 這個標記會出現在 LLM 輸出的文字裡**（B-1、B-2、B-4、B-7 都有），這不是要顯示的文字符號，是我們跟 LLM 約定的自訂標籤，前端要解析這個標籤、把包在裡面的文字渲染成深紅色，標籤本身（`<r>` `</r>`）不能顯示出來。這塊麻煩前端先看一下要怎麼 parse，這是這次新加的規則，v1沒有。
- **B-1的「代表句子」這個區塊可能會被要求整個不顯示**：如果 LLM 找不到夠貼切的原話，會直接標記整個區塊 disable，前端要處理「這個區塊有時候整張卡片就是不出現」的情況，不能假設它一定有內容。
- **B-4行為模式排行榜筆數不固定**：規則是「最多3組，找不到足夠依據支撐的組數就寧可少於3組」，前端畫面不能寫死一定要顯示3條，要能處理0~3條的情況。
- **B-3情緒文字雲的資料格式是「詞＋權重」**，權重是這個詞出現在幾筆歷史事件裡，前端要決定權重怎麼對應到文字雲的字體大小比例，這塊我們規格沒定死具體換算公式，設計上你們可以自己抓一個合理的視覺呈現。

## 兩邊都要一起對齊的地方

B-2（共鳴之錨中間交集的職涯錨名稱）跟 B-7（職涯北極星的主要錨定）**規則上要求這兩處顯示同一個答案**，如果實際測試發現兩邊有時候顯示不一致，不是規格邏輯有問題，是實作上兩處各自呼叫、沒有共用同一次分析結果導致的，這塊麻煩前後端一起討論一次要怎麼確保這兩個畫面區塊用的是同一筆分析結果，不要各自重新問 LLM 一次。
